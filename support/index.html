Quick start

Move one value in three steps

  1. Choose the field.Right-click the exact editable field and choose Fill from Phone.
  2. Scan once.Open the one-time QR with your phone camera.
  3. Send one value.Enter or paste it on the phone, send it, then review the filled field.

No account or phone app is required. The extension does not use the clipboard or submit the destination form. Without the extension, use secure web copy and paste; it decrypts locally, then you copy the value into the destination yourself.

What can I transfer?

One short-text, long-text, or password value. Supported targets include text, email, password, search, telephone, URL, textarea, and editable-content fields. The phone presents the matching input type, including a masked password control.

How does web copy and paste differ from the extension?

The web receiver uses the same one-time encrypted handoff, but browser isolation prevents it from filling a field on another website. It reveals nothing by default. You explicitly copy the received value, its mutable application buffer is immediately overwritten, and you paste it into the destination.

The browser and operating system control the clipboard, so Fill from Phone cannot prove or force clipboard erasure. Use the extension when avoiding the clipboard is more important.

Troubleshooting

Fix the common problems first

The transfer stopped or did not fill. What should I check?
  • Use Chrome 120 or newer and confirm the extension is detected on the test page.
  • Start again if the QR is more than two minutes old or was already scanned.
  • Keep the original page and selected field open until delivery finishes.
  • Try the test page. Chrome internal pages, replaced frames, removed fields, navigation, and changed field types stop safely rather than redirecting the value.
Why does my phone's password manager not offer the credential?

Password managers normally bind credentials to a website origin. The transfer page and destination site have different origins, so the manager may not suggest the destination credential. Open the password manager and copy the one value manually. A versioned, advisory destination hint is available for future password-manager integrations, but current managers are not required to use it.

How it works

One encrypted handoff, then expiry

How does the value move from phone to field?
  1. The extension creates an ephemeral P-256 key and independent one-time route, read, write, and challenge values.
  2. The QR carries public bootstrap data in its URL fragment, which browsers do not send in HTTP requests.
  3. The phone claims the transfer, derives the content key, and encrypts the value before upload.
  4. The relay delivers one opaque envelope. The extension authenticates the original route, origin, field type, and expiry before decrypting and inserting the value.

The relay reservation excludes the destination origin and field classification. The destination page sees the value only after the extension inserts it.

Can the QR be reused, and what remains after Send?

No. The first valid scanner claims the transfer, later claims fail, and the QR disappears from the desktop. The phone clears its visible control after encryption; the relay removes the envelope after delivery or expiry and retains only a short-lived consumed marker to reject replay. All active state expires within two minutes, and Fill from Phone creates no account or recoverable transfer history.

A captured QR can still race the intended phone for the first claim. First claim prevents a second delivery; it does not prove the scanner's identity.

Security and privacy

What the design protects—and where it ends

Can the relay read or retain the transferred value?

No decryption path exists in the reviewed relay. It receives short-lived session metadata, capability hashes, transient bearer capabilities, and the opaque encrypted envelope—not private keys, the derived content key, or plaintext. This is relay opacity, not a formal zero-knowledge proof protocol: the phone and extension are endpoints and necessarily handle plaintext.

For the full data-handling record, including routine network metadata, read the Privacy page.

Release checks also cover concurrent first-claim behavior, single consumption, replay rejection, authenticated route, origin, field, version, challenge and expiry binding, and the absence of decryption paths in the relay.

This is code-level regression evidence. It does not establish CAVP or CMVP validation, FIPS-validated operation, FedRAMP authorization, an ATO, an independent audit, or a penetration test.

What does end-to-end encryption not protect?

It cannot protect plaintext from compromised phone or extension code, browsers, operating systems, keyloggers, screen capture, password managers, or the destination page after insertion. Browser code also cannot prove physical erasure from device memory, swap, screenshots, or telemetry. The web-delivered phone sender inherits trust in code delivered by its origin.
